# QR Sign-in Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A screen with no session shows a QR code; an already signed-in phone scans and approves it; the screen receives its own never-expiring operator token.

**Architecture:** An in-memory store of pending device requests (`backend-rs/src/device.rs`, held on `AppState`) behind three public/authed route groups in `backend-rs/src/api/device.rs`. The token row is minted on the first successful poll after approval and cached for 60 s for retries. The dashboard gets a QR panel inside `TokenGate` and a lazy `/device` approve page.

**Tech Stack:** Rust (axum, sqlx/SQLite, tokio), React 19 + Vite, `node --test` for dashboard tests, a small QR library (`qrcode-generator`, no dependencies).

**Spec:** `docs/superpowers/specs/2026-10-21-qr-sign-in-design.md`

## Global Constraints

- Request lifetime: 5 minutes (`300` seconds). The waiting screen requests a fresh QR when it expires.
- Poll interval: about 2 seconds.
- Screen tokens: `flatline_op_` prefix via `auth::mint_op_token`, `expires` NULL, `active` 1, never expiring.
- The QR carries only the request code, in the URL fragment: `<base>/device#<code>`. `<base>` is `config.public_url` when set, else `window.location.origin`.
- The poll secret is returned by `start`, kept in the waiting screen's memory, and never put in the QR or a URL.
- Names: trimmed, 1 to 60 characters, duplicates allowed. Default name is derived from the user agent ("Chrome on Linux").
- No confirmation code (owner decided). No expiry on screen tokens (owner decided).
- Requests carry codes in JSON bodies, never in paths or query strings.
- Pasting a token keeps working. `TokenGate`'s paste form stays as a fallback.
- Backend lives in `backend-rs`; run its tests with `cargo test --manifest-path backend-rs/Cargo.toml`. Dashboard tests: `npm run test:dashboard`. Dashboard typecheck: `npm --prefix apps/dashboard run typecheck`.

## Review Focus

- Someone who photographs the QR and polls with only the code: gets `pending`/`unknown`, never the token (Task 1, Task 2).
- Poll after approval is lost, then retried within 60 s: same token returned, only one `tokens` row exists (Task 2).
- Poll after the 60 s retry window: `expired`, no second token (Task 1).
- Approve twice, approve after deny, approve after expiry: second call fails with a clear message and mints nothing (Task 1, Task 2).
- Flood of `start` calls: the pending map stays at its cap and a legitimate `start` is refused with 429, not silently dropped (Task 1, Task 2).
- Phone not signed in when it opens `/device#code`: it sees the token gate, and after signing in lands on the approve page with the code intact (Task 5).
- Server restart while a TV is waiting: its poll gets `expired` and it requests a new QR automatically (Task 4).
- Waiting screen unmounted mid-poll (route change, deploy reload): no further requests, no state update on an unmounted component (Task 4).

### Task 2: Device sign-in routes

**Files:**

- Create: `backend-rs/src/api/device.rs`
- Modify: `backend-rs/src/api/mod.rs` (declare module; register public routes in the `public` router next to `auth/login`, authed routes in `authed`)
- Modify: `backend-rs/src/api/openapi.json` and `docs/api.md` (document all five routes; `tests/completeness.rs` checks the OpenAPI document)
- Test: `backend-rs/tests/device_auth.rs`

**Interfaces:**

- Consumes: `DeviceRequests` from Task 1 (`state.devices`), `auth::mint_op_token`, `auth::hash_token`, `state.events.invalidate()`.
- Produces (JSON over HTTP, all bodies carry the code, none carry it in the path):
  - `POST /api/v1/auth/device/start` (public), body `{}` → `200 {ok, code, pollSecret, expiresIn, publicUrl}`; `publicUrl` is `config.public_url` or null. User agent comes from the `User-Agent` header. `Full` → 429 `{error:"busy"}` with a hint.
  - `POST /api/v1/auth/device/poll` (public), body `{code, pollSecret}` → `{ok, status:"pending"|"denied"|"expired"}` or `{ok, status:"approved", token}`. On the first poll after approval, insert the `tokens` row (same SQL as `api_keys::create` with `expires` NULL) using the approved name, call `record_delivery`, call `state.events.invalidate()`. Later polls inside the retry window return the same token and insert nothing.
  - `POST /api/v1/auth/device/lookup` (authed), body `{code}` → `{ok, userAgent, ageSeconds, suggestedName, publicUrl}`; unknown or finished request → 404.
  - `POST /api/v1/auth/device/approve` (authed), body `{code, name}` → `{ok}`; 409 `{error:"not_pending"}` with message when already decided or expired; 400 for a bad name.
  - `POST /api/v1/auth/device/deny` (authed), body `{code}` → `{ok}`; same 409 rule.
- `suggestedName` is a function `fn suggest_name(user_agent: &str) -> String` in `device.rs` ("Chrome on Linux", falling back to "New screen").

## Self-review notes

- Spec coverage: QR everywhere (Task 4 in `TokenGate`, which both mount sites use), approve page with name, UA and age (Task 5), per-screen minted token (Task 2), never expires (Task 2 test), poll secret, mint-on-delivery with 60 s cache, states and messages, fragment URL, `public_url` fallback and mismatch warning (Tasks 3 and 5), caps and rate limiting (Task 1 and 2), name validation (Task 1), last-used display (Task 6), docs (Tasks 2 and 6).
- One deliberate departure from the spec: it said `start` is rate limited per IP. `api/limits.rs:30-35` records that per-IP limiting is not meaningful behind the Cloudflare Tunnel and that forwarded-for headers are spoofable, so this plan uses a global cap of 64 pending requests with a 429 when full. The cost is that a flood can briefly stop a new screen from starting a request; the owner can still paste a token.
- Names used across tasks: `DeviceRequests`, `PollOutcome`, `startDeviceSignIn`, `pollDeviceSignIn`, `lookupDeviceRequest`, `approveDeviceRequest`, `denyDeviceRequest`, `approveUrl`, `codeFromHash`, `qrSvg`, `hostMismatch`, `runDeviceSignIn`, `isDeviceApprovePath`, `DeviceSignIn`, `DeviceApprove`.
